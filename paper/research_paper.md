## Abstract
Large language models (LLMs) specialized for software engineering frequently generate code containing security weaknesses. A widely proposed automated mitigation strategy is *scanner-guided repair*, wherein a static application security testing (SAST) tool inspects generated code and feeds diagnostic alert messages back to the model to guide an iterative fix. In this preliminary working paper, we investigate the **"Whack-a-Mole" hypothesis**: when an AI model repairs generated Python code using actual static-analysis findings, does the repair remove existing alerts while leaving some unresolved, introduce new secondary alert instances, or increase structural code complexity?

We establish an automated evaluation harness coupling the LLMSecEval benchmark, the official GitHub CodeQL CLI (evaluating 52 security and taint-tracking queries), and the open-weight **Qwen2.5-Coder-1.5B-Instruct** model across three controlled experimental conditions: *(A) Baseline generation*, *(B) Security-aware prompt prefixing*, and *(C) Closed-loop scanner-guided repair*. Before experimental execution, we validate the CodeQL harness against ground-truth positive (Flask untrusted redirect in debug mode) and negative controls, confirming identical detection across CSV and SARIF outputs. In an initial three-task pilot evaluation (sample size N = 3 Python tasks from LLMSecEval), we observe that: (1) security-aware prompting was completely ineffective at suppressing baseline alerts (100% alert persistence across all 4 baseline alert instances); (2) scanner-guided repair resolved a localized configuration flaw ("Flask app is run in debug mode", 1/4 alerts, 25.0% resolution rate), but failed to eliminate dataflow taint-tracking alerts ("URL redirection from remote source", 3/4 alerts, 75.0% persistence rate); (3) no new secondary findings were introduced in evaluable cases (New = 0 alert instances); and (4) Radon cyclomatic complexity and logical lines of code remained unchanged across repairs (change in CC = 0, change in LOC = 0; mean CC = 1.33, mean LOC = 11.0). While constrained by a pilot sample size, these preliminary findings suggest that naive diagnostic feedback enables models to patch literal configuration flags but fails to prompt architectural sanitization for dataflow vulnerabilities, highlighting the need for structured template guidance in automated AI program repair.

**Keywords:** AI Code Generation, Automated Program Repair, Static Application Security Testing, CodeQL, Vulnerability Remediation, Whack-a-Mole Effect, Software Security.

## 1. Introduction

The integration of Large Language Models (LLMs) into code generation workflows has accelerated developer velocity but introduced substantial security concerns. Seminal empirical studies report that approximately 40% of code completions generated by state-of-the-art models contain security vulnerabilities, including Common Weakness Enumerations (CWEs) from the MITRE Top 25 (Pearce et al., 2022; Tony et al., 2023).

To address this challenge, two prompt-engineering remediation strategies are commonly deployed:
1. **Security-Aware Prompting:** Instructing the model *a priori* through a system or user prompt constraint to generate secure, vulnerability-free code.
2. **Scanner-Guided Repair:** Analyzing candidate completions with a Static Application Security Testing (SAST) tool and feeding the diagnostic error text (rule identifier, error message, line location) back to the LLM to request a targeted repair.

While scanner-guided repair represents an intuitive closed-loop approach, practitioners in program repair have observed a potential drawback metaphorically termed the **"Whack-a-Mole" effect**: attempting to resolve one static analysis finding may cause the model to introduce secondary bugs elsewhere, shift taint sinks, or inflate code complexity through bloated wrappers without actually resolving the root security weakness.

### 1.1 Scope and Research Questions
This paper presents a **preliminary pilot study** investigating the feasibility and dynamics of closed-loop CodeQL repair on Python code. We formulate three exploratory research questions:

- **RQ1 (Alert Resolution vs. Persistence):** *To what extent does feeding authentic CodeQL static-analysis findings back to the model result in the complete elimination versus persistence of original alert instances?*
- **RQ2 (Secondary Finding Introduction):** *Does scanner-guided repair introduce new, distinct static-analysis findings not present in the baseline code (the Whack-a-Mole dynamic)?*
- **RQ3 (Structural Code Complexity):** *Does scanner-guided repair alter the structural complexity of generated code, as measured by Cyclomatic Complexity (CC) and Logical Lines of Code (LOC)?*

## 3. Experimental Methodology

### 3.1 Experimental Conditions
We specify three controlled experimental conditions:

- **Condition A (Baseline Generation):** The model receives the raw natural language specification from the benchmark without security instructions:
  $$\mathcal{P}_{\text{base}} = \text{Prompt}_{\text{LLMSecEval}}$$
- **Condition B (Security-Aware Prompting):** The baseline prompt is augmented with an explicit security directive:
  $$\mathcal{P}_{\text{sec}} = \mathcal{P}_{\text{base}} \cup \{\text{"Ensure code is secure and mitigates CWEs"}\}$$
- **Condition C (Scanner-Guided Repair):** If Condition A generates code $\mathcal{C}_A$ yielding a non-empty set of CodeQL alerts $\mathcal{A}_A = \{a_1, a_2, \dots, a_k\}$, we construct a diagnostic prompt containing the exact rule identifiers, descriptions, and line locations:
  $$\mathcal{P}_{\text{repair}} = \text{FormatPrompt}(\mathcal{C}_A, \mathcal{A}_A)$$
  If $\mathcal{A}_A = \emptyset$, Condition C is recorded as clean, and repair is not invoked (avoiding false repair counts).

### 3.2 Evaluation Engine and Query Suite
We deploy the standalone **GitHub CodeQL CLI** (bundle v2.24.x) executing the official `codeql/python-queries:codeql-suites/python-security-extended.qls` suite. This suite encompasses 52 comprehensive rules covering:
- Injections: SQL Injection (CWE-089), Command Injection (CWE-078), Code Injection (CWE-094), LDAP Injection (CWE-090).
- Web Security: Untrusted URL Redirection (CWE-601), Reflected XSS (CWE-079), CSRF Disabled (CWE-352).
- Sensitive Data & Configuration: Flask Debug Mode (CWE-215), Cleartext Logging (CWE-312), Hardcoded Credentials (CWE-798).

### 3.3 Verification of Ground-Truth SAST Controls
To eliminate threats of scanner misconfiguration or silent parsing failures, we executed ground-truth control validations (`tests/test_codeql_controls.py`) prior to experimental execution:
- **Known-Positive Control:** A Flask web endpoint accepting an unvalidated URL query parameter and running in debug mode.  
  *Result:* CodeQL flagged exactly **2 alerts** (`py/flask-debug` [CWE-215] and `py/url-redirection` [CWE-601]), verified identically across both CSV and SARIF outputs.
- **Known-Negative Control:** An internal static redirect (`redirect("/dashboard")`) with debug disabled (`debug=False`).  
  *Result:* CodeQL produced **0 alerts**, verifying 100% precision on baseline controls.

### 3.4 Model Selection and Execution Context
- **Evaluated Model:** `Qwen/Qwen2.5-Coder-1.5B-Instruct` (pinned revision: `main`).
- **Generation Parameters:** Temperature $T = 0.2$, Seed = 42, Max New Tokens = 512, deterministic greedy decoding.
- **Hardware & Implementation Note:** The primary target model for cloud scaling is `Qwen/Qwen2.5-Coder-7B-Instruct` (configured with `BitsAndBytesConfig` 4-bit quantization). However, during local execution on a Windows host lacking a CUDA-enabled PyTorch wheel, loading the 7B model in 32-bit float exceeded the contiguous system RAM allocation threshold (>15 GB). To maintain experimental validity without corrupting environment state, the automated runner activated the pre-specified fallback model `Qwen/Qwen2.5-Coder-1.5B-Instruct`. All results reported in this paper stem exclusively from this 1.5B model run; results from different model sizes are never mixed.

## 6. Discussion and Preliminary Observations

### 6.1 RQ1: Alert Resolution vs. Persistence
Across the evaluated pilot sample, **75% of baseline alert instances persisted** following scanner-guided repair. A distinct asymmetry emerged based on the structural nature of the finding:
- **Configuration-Level Vulnerabilities:** In task `CWE-20_IIV-1c`, the model successfully eliminated `Flask app is run in debug mode`. This fix required altering a single literal argument (`debug=False`), which the model parsed directly from the diagnostic description.
- **Dataflow Taint-Tracking Vulnerabilities:** In contrast, `URL redirection from remote source` (CWE-601) persisted across both tasks `CWE-20_IIV-1b` and `CWE-20_IIV-1c`. Remediating an open redirect requires constructing validation logic (e.g., parsing netloc or checking a domain whitelist). When provided only with the alert description, the model either repeated the direct redirect call or added cosmetic commentary, failing to synthesize a valid sanitizer.

### 6.2 RQ2: The Whack-a-Mole Dynamic in Evaluated Tasks
In this three-task pilot, **zero new alert instances were introduced** ($\text{New} = 0$). While this pilot does not demonstrate secondary bug explosion in concise snippets, it reveals an equally critical failure mode: **vulnerability inertia**. Rather than introducing novel defects, the model predominantly regenerated the same insecure dataflow patterns despite explicit scanner warnings.

### 6.3 RQ3: Impact on Structural Code Complexity
Radon Cyclomatic Complexity remained constant ($\text{CC} = 2 \rightarrow 2$), and LOC remained stable ($11 \rightarrow 11$ and $12 \rightarrow 12$). This confirms that the model did not introduce convoluted defensive branching, but also explains why the taint-tracking alerts persisted: no validation branches were added to intercept the untrusted dataflow.

## 7. Threats to Validity and Limitations

1. **Pilot Sample Size:** This study reports on an initial pilot of 3 Python tasks from the 83-task benchmark. The findings are hypothesis-generating and should not be generalized to all CWE categories or large-scale codebases without completing the full benchmark.
2. **Model Specificity:** Results reflect the capabilities of `Qwen2.5-Coder-1.5B-Instruct`. Larger frontier models (e.g., 7B, 32B, or proprietary models) may exhibit different repair dynamics.
3. **Static Analysis as a Proxy:** CodeQL alerts indicate static pattern matches and dataflow paths, not confirmed dynamic exploitability.
4. **Absence of Functional Testing:** Functional unit tests were not executed; repairs could theoretically alter intended program semantics while suppressing warnings.

---

## 8. Conclusion and Future Directions

This preliminary study validates an automated evaluation framework for closed-loop AI code repair using CodeQL and LLMSecEval. Our pilot results indicate that general security prompt constraints are ineffective, and raw SAST feedback readily fixes trivial configuration flags but struggles with complex dataflow taint flows. Future work will deploy the validated Kaggle pipeline to scale across the complete 83-task benchmark, evaluate larger model architectures (7B and 32B), and explore multi-agent repair workflows incorporating structural sanitizer templates.
